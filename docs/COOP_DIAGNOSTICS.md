# Логи настоящего коопа

В сборке 0.6.1 журнал включается автоматически при создании комнаты или
подключении. Он работает и в лобби, и в забеге, на компьютере каждого игрока.
Python и дополнительные программы для записи не нужны.

## Что сделать во время игры

1. Если появились рывки, нажмите **F8**. Это поставит метку с текущими
   показателями, не приостанавливая бой. Короткий звук подтверждает нажатие.
2. После игры выйдите обычным способом, чтобы завершить запись.
3. Откройте **«Настройки» → «Папка логов»**. Кнопка работает и из главного меню.
4. Пришлите ZIP этой папки **с компьютера ведущего и проблемного клиента**.
   Если дёргалось у всех — полезны журналы всех участников. Укажите, у кого
   была проблема и примерно когда; метки F8 помогут найти точный момент.

Игровая папка данных — `user://logs/`; файлы сетевых журналов начинаются
с `survivors_coop_`. Суффикс `.active.jsonl` означает текущую или оборванную
запись: её тоже можно прислать после аварийного закрытия. Завершённые части
имеют суффикс `.jsonl`. В той же папке могут быть стандартные `godot.log`
с сообщениями движка.

## Что записывается

- Версия игры/протокола/движка, роль ведущего или клиента, игровой ник,
  идентификаторы участников, ОС, видеокарта и число логических процессоров.
- Раз в секунду — FPS, среднее/95-й перцентиль/максимум времени кадров,
  симуляции, подготовки снимков, отрисовки команд и интерполяции клиента.
- Пинг и его вариация отдельно по каждому соединению, оценка потерь
  **надёжных** пакетов ENet, throttle, принятые снимки и их возраст.
  Эти потери не выдаются за точный процент потерь всех UDP-пакетов.
- Последовательность и подтверждение ввода, размер очереди, пропуски,
  коррекция позиции в пикселях, исходная позиция сервера и результат
  повторного расчёта неподтверждённых команд.
- Количество мобов, снарядов и эффектов, позиции, жизни, паузы и выбор
  улучшений всех героев. Указывается, являются ли позиции серверными
  или уже интерполированными для отображения.
- Подключение/отключение, барьер загрузки, seed и эпоха забега,
  паузы/команды, сюжетные переходы, заметные коррекции и долгие кадры.

`t_ms` — монотонное время от открытия журнала, `wall_ms` — время UTC Unix,
`tick` — серверный такт (на клиенте последний принятый). Поэтому журналы
нескольких ПК можно сопоставить даже при различии локальных часов.
Пропущенные периодические обновления означают устаревание состояния в
приложении; это также может быть переупорядочивание, а не потеря UDP-пакета.

В сетевом JSONL есть игровые ники и игровые данные. Пароли, переписка, ZeroTier
Network ID и IP-адреса не собираются. Автоматической отправки файлов нет.

## Размер и нагрузка

Запись выполняет отдельный поток; главный поток не ждёт дисковых операций
во время боя. Очередь ограничена 256 записями, выборки — 600 значениями на
метрику за окно, повторные события коррекций ограничены по частоте.
Переполнение очереди явно отмечается счётчиком `writer.dropped`.

Каждая часть ограничена **4 МиБ**. Сохраняются **12 завершённых частей** и
текущие записи. Активные записи других экземпляров игры не удаляются;
оборванные `.active.jsonl` рассматриваются для очистки после суток без
изменений. Закрытие сеанса дожидается выгрузки очереди. Сетевые и игровые
часы, урон и RNG журнал не изменяет.

## Разбор для разработчика

```sh
python scripts/analyze_coop_logs.py путь/к/папке --output report.json
python scripts/analyze_coop_logs.py host.zip friend.zip --output report.json
./.tools/Godot_v4.7.2-stable_linux.x86_64 --headless --path . -s qa/test_coop_logging.gd
```

Анализатор читает JSONL напрямую и из ZIP, объединяет части по сеансу,
показывает пики, RTT, метки и завершение. Повреждённая последняя строка
после аварии учитывается отдельно и не мешает прочитать остальные данные.
Он ничего не отправляет и не ставит диагноз автоматически.

Например, `WAITING` при `phase=LEVEL_UP` у товарища объясняет общую остановку
боя без сетевой неисправности. Большой `snapshot_gap_ms` при нормальных
временах симуляции — повод смотреть канал; большой `simulation_ms` у ведущего
— расчёт мира. Реальную причину нужно подтверждать по совпадающим тактам,
меткам и журналам обеих сторон.
`scene_changed=true` у большой коррекции означает постановочный переход;
такая запись сама по себе не доказывает сетевой рывок.

Проверки: [coop_logging_results.json](../qa/coop_logging_results.json).
Двух- и четырёхпроцессные сценарии дополнительно проверяют настоящие файлы:
выборки времени кадров, метку и закрытие записи без потерь очереди.
В 11 итоговых сетевых сценариях проверен 41 журнал без повреждённых строк
и потерь очереди; отдельно проверены ZIP и оборванная последняя строка.
Сводка: [coop_four_verification_summary.json](../qa/coop_four_verification_summary.json).
